## 2. `PLAN_GAP`（方案内部冲突）

### PG16：`verificationTemplateData.AppURL` 不满足同节的“一个字段都不多”硬规则

冻结方案 §7.1 同时规定：

1. 验证码模板数据结构含 `AppURL string // FRONTEND_ORIGIN`（`:929-934`）；
2. 不得把配置对象或 `os.Environ()` 的产物放进数据结构，且验证码模板数据“只能包含内置模板今天已经渲染出来的信息，一个字段都不多”（`:958-960`）。

BASE 的验证码邮件只渲染以下信息（`server/internal/service/email.go:340-363`）：验证码、固定的 10 分钟提示、固定文案，以及 Subject 中的 `Multica` 字面量。它不读取 `FRONTEND_ORIGIN`，正文和主题也都不包含应用 URL。`FRONTEND_ORIGIN` 目前只在邀请邮件路径读取（`:368-373`），用于构造 `InviteURL`。

因此，按方案给出的结构体加入 `AppURL` 会把一个验证码邮件今天没有渲染的信息暴露给模板，违反同节的硬规则；删掉 `AppURL` 又不再实现方案明列的数据白名单。两者无法同时满足，且方案自己的 L2 `must_answer` 5（`:1243-1244`）已经提出同一问题，但正文没有给出裁决。

这不是命名或测试写法差异，而是模板数据授权面的选择。实现不能自行决定以下二者之一：

1. **收紧白名单**：从 `verificationTemplateData` 删除 `AppURL`，继续维持“只含既有可见信息”的硬规则；或
2. **扩大契约**：保留 `AppURL`，明确撤回/改写“一个字段都不多”，并说明为什么把 `FRONTEND_ORIGIN` 新暴露给验证码模板仍符合数据最小化与安全边界。

`AppName` 可由现有 Subject 的 `Multica` 字面量解释为既有可见信息；本 finding 只阻断无现有落点的 `AppURL`，不扩大到已经可由 BASE 证明的字段。
