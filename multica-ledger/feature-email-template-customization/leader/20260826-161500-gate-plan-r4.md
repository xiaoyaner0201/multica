## 5. PG20（新，本次核对发现，**非阻塞**）

**`AppName` 通过了字段准入判据，却没有通过 §0.8.3 用来删掉 `AppURL` 的那条决定性判据；
r4 没有把两者放在一起比较过。**

事实（我复算）：

- r4 全文**没有任何 `AppName` 的赋值处**（`grep -n 'AppName:'` 零命中）。
- r4 引入的新配置项**只有 `EMAIL_TEMPLATE_DIR` 一个**（穷举 r4 中全部 `*_[A-Z_]+` 形态的配置名），
  没有任何品牌名配置项。
- 因此 `AppName` 的取值由 INV13 + §7.1.1 的 `g` 隐式确定：
  `g`(主题 `Your Multica verification code`) = **字面量 `Multica`**。

两点后果：

1. **推理不对称。** §0.8.3 说删 `AppURL` 的「决定性」理由是**能力增量为零**——
   值是部署期常量，写模板的运维方本来就有，自己敲一行即可。这条对 `AppName` **同样成立，
   而且更强**：运维方比谁都清楚自己的品牌名。r4 对 `AppName` 只回答了准入判据（`g` 存在），
   从未回答那条决定性判据。上游 reviewer 一定会问「`AppURL` 因为运维方自己能敲所以删了，
   那 `AppName` 呢」，而方案里没有答案。
2. **对本功能的目标用户是个陷阱。** 若 `AppName` ≡ `Matica` 之外的任何值都不被允许，
   那么自建部署方在自己的模板里写 `{{.AppName}}`，渲染出来的是**上游的品牌名 `Multica`**。
   一个专为「让自建部署自定义对外邮件」而做的功能，提供一个名叫 `AppName`、
   却硬编码别人品牌的变量，是可预见的误用点。

**为什么判非阻塞**：取值是确定的（INV13 已经把它钉死），INV13 与 T26 自洽，实现不需要自行决定，
stage 2 可以在不解决 PG20 的情况下正确进行。它是**论证缺口与文档缺口**，不是未决裁决——
这一点与 PG16 有本质区别，我不把两者等同。

**处置**：带进闸门 1 一并呈给发起人。理由是三条出路里有两条是产品取向而非工程判断：
(a) 删 `AppName`，与 `AppURL` 一致；(b) 留，但 T21 四语言文档必须写明它固定渲染 `Multica`、
自建方要用自己的品牌请直接写在模板里；(c) 留并新增品牌名配置项——但 (c) 会**违反 r4 自己刚写的
判据**（运维方的品牌名不在 BASE 输出字节里），若要走 (c) 必须显式修订判据，即回到规划。
我不代发起人选。

**我自己的划界**：`AppURL` 我判为阻塞、`AppName` 判为非阻塞，差别不在字段大小，
在**实现是否被迫替规划做决定**。`AppURL` 那次两条规定互斥、实现无论选哪边都在裁决；
`AppName` 这次方案是自洽的，只是没把话说完。

## 6. 过程摩擦

**M-L22（新）：`cp` + 逐处 commit 这个做法，第一次真正省下了核对成本，应写进正本。**
r4 是 2457 行、r3 是 1853 行，人工比对不现实。规划先用一个 commit 落逐字节副本，
之后每处修改一个 commit，于是「完整且唯一的修改集」= 一条 `git diff`。
我核「未重开已放行方向」只花了一条命令 + 43 个 hunk 的浏览，而不是通读全文。
**建议正本要求**：凡以既有产物为基底的修订版（rN → rN+1），必须以逐字节副本单独起一个 commit，
核对方据此取得完整修改集；否则修订版与重写版在核对方眼里无法区分。

**M-L23（新）：规划这次主动执行了核对方的判据，而不是等核对方来查。**
M-L18（逐元素回归）与 M-L19（`must_answer` 扫描）本来是我写给**核对方**的建议，
规划把它们当作**自己的自查清单**先跑了一遍，跑出 PG17/PG18/PG19 三处并各自裁决。
其中 PG19 是它自曝「r3 里同样的错误我犯了两次，只被抓到一次」。
这比我抓到它便宜得多——同一个缺陷，在方案阶段自查出来是改一段文字，
在实现阶段撞出来是整条链返工（PG16 就是后者，代价是一次实现 Run + 一次闸门白批）。
**建议正本明确**：核对判据一律**双向公开**——写进 gate 清单的同时写进产出方的自查清单。
判据不是核对方的私器；让产出方先跑，核对方才有余力去找判据没覆盖的东西（本轮的 PG20 正是如此）。

**M-L24（新）：我这轮的第一个复算命令是错的，差一点报出一个假 finding。**
我用 `grep -c '71'` 比较 r3/r4 中 `71` 的出现次数，得到 r4 **更多**，看上去像是 PG15 没做。
实际是该模式匹配了日期与哈希里的 `71`。改用 `\b71\b` 后，r4 的每一处残留都是删除记录。
**与 M-L11 同源但不同因**：M-L11 是「没按记录的构造复算」，这次是「用了一个比断言更宽的匹配」。
**建议**：核对方复算一个**计数**类断言时，必须先验证匹配模式在**已知答案**的样本上正确
（例如先在 r3 上验证 `\b71\b` 只命中那几处例证），再拿去跑待核对产物。
