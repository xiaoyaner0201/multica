## 4. 处置：改掉产出方式，保留产出形态

派单已追加修订，**要求不变、方法改变**：

- r3 **仍然是完整可独立阅读的单一文档**（这个性质是为实现服务的，不放弃——
  实现不该在两份文档之间做心算合并，PG11 那类事故正是从「判据分散」来的）；
- 但它**不通过重新生成全文得到**，而是
  `cp planner/20260826-121052-plan-r2.md planner/<ts>-plan-r3.md` 之后**做定点编辑**。
  未改动的章节是**文件复制的结果**，不是模型重新输出的结果。
- 增量分段提交：每改完一处就 `commit` + `push`（全 refspec），不攒到最后。
  这样即使 Run 再次中途失败，也留下可续接的持久化状态，而不是又一次零产出。

附带收益与代价各一条：复制保证了未改动章节**逐字节不变**（比"原样带过来"这种承诺强得多，
是可 `git diff` 验证的机械性质，我核对时会用 `git diff r2 r3` 直接读出改动集）；
代价是 r3 的 front matter 与 §0 需要显式改写，否则会留着 r2 的 `ts`/`verdict`/标题。

## 5. 流程摩擦

  我一直把派单正文当作「说清要什么」的问题，本次暴露出它同时是「要多少」的问题。
  正本的模板给的是**结构**（章节清单），没有任何一处提示产出规模的上界或增量落盘的义务。
  建议正本补一条：**产物预计超过既有同类产物规模时，派单必须给出增量落盘方式**——
  分段 commit、或基于已有文件的定点编辑，而不是一次性全文生成。
  这条对账本尤其重要，因为账本是跨卡片的唯一通道，**未 push 的分录对下游等于不存在**，
