## 4. 本次 finding

### PG10（`PLAN_GAP`）：CJK 主题在 998 octet 之下的有效长度是 **91 rune**，不是「约 81」

r2 在至少五处写「~81 rune」/「约 80 字」：§2 的 Q5 背景、§1.4 A7、T23 的预期
（「rune 数被进一步截断到 ~81」）、L3 `must_answer` 6（「从 200 字压到约 80 字」）、
以及 §14 交给文档面的写作要求（T21「文档写明 CJK 主题有效长度约 80 字」）。

我的复算（度量口径与 INV11 相同，`len("Subject: " + QEncoding.Encode("utf-8", s))`）：

```
CJK n=90 -> 987 octet
CJK n=91 -> 996 octet     <- 998 之下的最大 rune 数
CJK n=92 -> 1018 octet
```

**91，不是 81。** 论证方向不受影响（200 → 91 仍然是显著压缩），但三处后果是实的：

1. **T23 断言了一个会失败的具体数字。** 这正是 PG3/PG5 那一类——「断言了具体值，没回到管线里核对」。
2. **Q5 是本轮闸门 1 唯一的确认项，而它的背景数据错了。** 我不能拿一个自己刚复算出不同结果的数字
   去问发起人。发起人要裁决的正是「压到多少还能接受」，那个数字就是决策依据本身。
3. **T21 要求把这个数字写进四语言文档**，错值会一路落到用户可见面。

### PG11（`PLAN_GAP`）：T24 的边界构造在 r2 给出的语境里造不出来

T24：「主题模板渲染出**恰好使 `Subject:` 行等于 998 octet** 的内容 → 不被截断；再加一个 rune 则被截断」。

`QEncoding` 对 CJK 的量化步长是 9 octet/rune，且在 encoded-word 边界上跳变：

```
n=91 -> 996 ; n=92 -> 1018          （跳 22，998 被整个跳过）
纯 CJK 在 1..300 rune 范围内，命中 998 的 rune 数：无
纯 ASCII 命中 998 需要 989 rune —— 但 200 rune 上限先生效，200 ASCII rune 只有 209 octet，永远够不着
```

也就是说，**在 r2 自己规定的管线里（先 200 rune 上限、再 998 octet 上限），
用 T23/Q5 通篇使用的纯 CJK 或纯 ASCII 构造，998 这个点不可达**。

它并非绝对不可达——我用混合宽度构造出来了：

```
22×"é" + 63×"中" + 109×"a" = 194 rune -> 恰好 998 octet；+1 个 ASCII rune -> 999
```

但 r2 没有给出任何这类构造，而实现拿到的是「渲染出恰好 998 octet 的内容」这句话。
按 T23 的语境去构造（CJK），它会发现从 996 直接跳到 1018，然后卡住——**与它前两次开工即停同型：
判据本身在管线里做不到。**

处置由规划裁决，我不代决。两个方向供参考：(a) 给出可复现的混合宽度构造串并写进 T24；
(b) 把 T24 从「命中 998」改写为**不动点性质**——「截断函数返回满足约束的最长前缀，且再接一个 rune 必然超限」，
这个性质对任意输入都成立，不依赖能否命中某个具体 octet 数。我倾向 (b)，因为它同时覆盖了
量化步长这个事实，而 (a) 会把一个偶然的构造串固化进测试。
