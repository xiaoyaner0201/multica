## 3. 追加约束二：把 header folding 记为已知正解，并说明为何不做

**放行人的技术判断（全文要点）**：截断是**次优解**。RFC 5322 §2.2.3 对超长 header 的正确处理是
折行（CRLF + WSP），而 RFC 2047 的 encoded-word 本身就是为可折行设计的——每个 encoded-word
可以独占一行。真正的原因是 Go 标准库的 `mime.QEncoding` 不折行，只产出单行。
本次**不做折行**，因为它会改动内置路径的共享代码，直接冲突「未配置时字节级零变更」。
但方案与 PR 描述都要写明：**折行是正解、截断是本次的范围内取舍、折行同时能修掉内置路径那个
1349 octet 的既有问题**。

### 3.1 我独立验证了这条判断的技术前提，成立

放行人这条不是意见而是事实断言，我按惯例自己跑（探针在仓库外，工作树保持 clean）：

```
encoded-word count = 18, longest = 75 octets
=> if folded (CRLF+SP before each word), longest line = 76 octets
RFC 2047 limit is 75; longest word within limit: true
=> folding fixes the 998 overflow for BOTH paths: true
```

**结论：折行确实是完整解。** Go 的 `splitWord` 按 RFC 2047 的 75 字符上限切分 encoded-word，
所以**每个 word ≤ 75 octet**；若在 word 之间写 `CRLF + SP` 而不是空格，每行 ≤ 76 octet，
远低于 998。这对**任意长度、任意字符集**的主题都成立，因而它不仅修掉自定义路径的越界，
**也彻底修掉内置路径那个 1349 octet 的既有问题**——放行人的判断成立，且是可机械验证的。

对照之下，截断是有损的（内容被丢弃），折行是无损的（内容全保留、只改换行）。
**「截断是次优解」这个定性准确，不是修辞。**

一处记账诚实性说明：我用近似构造（`"Invitation: " + 60×工 + " / " + 60×邀`）复现出 **1337** octet，
r3 §12 探针 R5 记的是 **1349**。差 12 octet 来自我猜的字面量前缀与真实内置模板不同。
**我不据此质疑 1349**——按 M-L11 的教训，复现不出先怀疑自己的构造；两者量级一致，
且本节结论（每 word ≤ 75）与前缀无关。PR 描述引用时用 r3 的 1349，不用我这个近似值。
